# Protocol catalog and library-selection evidence (RIL-104)

This page is the catalog source of truth for egress protocols: each protocol is either reviewed-and-admitted (with its library-selection conclusion and evidence) or explicitly not admitted (refused at assembly). The machine face lives in `crates/rillane-config/src/protocol_catalog.rs` (`CATALOG`); the sections below (`## <kind>`) are its evidence anchors, verified field-by-field by that module's contract tests. User-facing capability boundaries live in [PROTOCOLS](PROTOCOLS.md); the UDP capability face is the build-time scan (`scan_udp_capability`, runtime).

## Registration spec (Factory ladder)

A protocol reaches the hot path only by completing every rung; a missing rung is a refusal:

1. **Library-selection record**: fill the corresponding section here — candidate library version, license, platforms, public API, and the bypass/cancel/stats/reuse conclusions. A "no usable library" conclusion must be recorded too — missing implementation evidence is the precondition for self-writing, not a license to self-write.
2. **Catalog entry**: add an entry in `protocol_catalog.rs` (registration state, UDP column, `Backend` conclusion). Catalog size must equal the IR egress variant count; a contract test enforces the sync.
3. **IR variant**: add the `EgressConfig` variant (closed enum — uncataloged types cannot enter the config face).
4. **Connector wiring**: register the factory in the rillane-protocols/runtime build match. Not-admitted types are refused at assembly with stable codes — `config.egress.not_admitted` (cataloged, not admitted) / `config.egress.unknown` (outside the catalog).
5. **Acceptance**: real-peer verification, explicit refusal of unsupported combinations, bidirectional subscription-field conversion samples (the uniform acceptance of RIL-105..134, see root `todo.md`).

**Feature pruning** (extends the RIL-040 profiles): a protocol backend that is feature-gated (e.g. a `proto-<name>` feature) is refused at config-validation time with the stable code `config.combo.unsupported` in builds that lack the feature — never the hot path, never hidden degradation. Today every backend ships in the default profile; per-platform exceptions (WireGuard's android/armv7-ohos stubs) are recorded in their sections.

## Evaluation record template

Every admitted section carries these fields (the contract test checks each one; a missing field fails the test):

- **Conclusion**: selected library / self-written (self-writing requires the recorded no-library conclusion first)
- **Version**: version requirement (Cargo.toml) + lock-resolved version
- **License**: SPDX expression
- **Platforms**: support surface and exceptions (stubs are never silent)
- **Public API**: the library/module surface in use
- **Bypass**: whether the library's internal I/O can be bypassed (libraries that own dialing/encryption block pool and dial-policy composition — recorded honestly)
- **Cancel**: whether open-phase cancellation/deadline reaches into the library (uninterruptible libraries are stated)
- **Stats**: observability points (how failures surface; no observation points are recorded as unknown)
- **Reuse**: connection reuse / prewarm / multiplex conclusions

## shadowsocks

- **Cancel**: open-phase checks; the data plane cancels with the stream (no independent blocking section)
- **Stats**: cipher-parse failures are named at build time; SIP003 plugin mode is a process bridge — the plugin's own I/O is outside this repository's observation points (recorded honestly)
- **Reuse**: the UDP face reuses the TCP face's server_config (`from_connector`); plugin (SIP003) mode refuses UDP (SIP003 defines only a TCP data plane)

SS2022 password semantics are a base64 key whose length must exactly match the algorithm's key length (16 bytes for aes-128, 32 for aes-256/chacha20) — validated at construction. - **Server face (RIL-134)**: reuses the same library's server face — `ProxyListener` (TCP accept + handshake resolving the target `Address`; the decrypted stream is the Flow io) and `ProxySocket` (`UdpSocketType::Server` datagram unpack/pack). Self-writing adds nothing: cipher-state-machine correctness belongs to the library (client and server share one cipher core; RIL-131 already accepted all six methods against this real server face). Inbound role: `ShadowsocksIngress` (full TCP face plus a UDP face gated by `udp.enabled`/`udp_enabled`); the SIP003 plugin server face is not delivered (named); method/password validation matches the egress posture (`none` and uncompiled-feature names refused, SS2022 base64 key shape); UDP session lifetime belongs to the `UdpSessionTable` (same machinery as the socks5 ASSOCIATE: sticky routing, idle reclaim, chain-failure revocation).

## shadowsocks-shadow-tls

- **Conclusion**: self-written carrier (RIL-110) — no usable backend exists. Evaluation sweep (2026-11-17, crates.io API + GitHub source verification): the official `shadow-tls` crate (ihciah/shadow-tls, registry max 0.2.20, MIT, last publish 2023-04-18 — unpulled for three and a half years) is the only registry-published ShadowTLS artifact, and it is not embeddable here: (1) its lib root carries `#![feature(impl_trait_in_assoc_type)]` — nightly-only, it does not compile on the stable toolchain this workspace's gate runs on; (2) it is built on monoio (thread-per-core io_uring), not tokio — the workspace data plane is tokio end to end, and the public API is a listen-and-relay binary face (`ShadowTlsClient::new(listen_addr, target_addr, …)` + `serve()`), with no stream-level connect/accept API to wrap into EgressConnector/IngressEndpoint; (3) v3 additionally requires a rustls 0.20 fork (`rustls-fork-shadow-tls 0.20.9-mod.2`) to sign session_ids — adopting a second, stale TLS stack beside the shared rustls 0.23.46 face for a carrier is out of proportion. The registry query otherwise surfaces only rustls/monoio forks of the same project — no other ShadowTLS protocol library. Conclusion = self-write from the official protocol docs and source as wire ground truth (ihciah/shadow-tls tag `v0.2.20` shallow-read 2026-11-17: `docs/protocol-en.md` (v2 spec) + `src/helper_v2.rs` + `src/server.rs` `relay_v2`/`copy_until_handshake_finished` + `src/client.rs` `relay_v2`/`connect_v2` + `src/util.rs` framing constants).
- **Version**: in-tree implementation (no third-party protocol dependency); ShadowTLS **v2 exactly**. v1 is refused by name — officially last implemented at v0.1.4, its post-handshake traffic is unframed raw inner data and it has no active-probe defense (the official design doc presents v2 as its replacement). v3 is refused by name — its hijack-resistance machinery is not delivered: 4-byte session_id HMAC, ServerRandom extraction with the XOR SHA256(PreSharedKey+ServerRandom) transform of every handshake-server frame, bidirectional 4-byte stream HMACs, muddled-request fallback, strict-mode TLS1.3-only handshake relay. Carriers rustls fork 0.23.46 / tokio already pinned workspace-wide; the client needs NO TLS-library fork for v2 (the challenge is injected by a stream wrapper around the post-handshake writes, not by patching rustls).
- **License**: repository license (self-written)
- **Platforms**: follows target-platform TCP support (pure TCP carrier — no QUIC/io_uring surface)
- **Public API**: `ShadowsocksShadowTlsConnector` (crates/rillane-protocols/src/outbound/shadowtls.rs — the SS TCP face carried over the v2 carrier, composed via `ProxyClientStream::from_stream`, the shadowsocks crate's stream-injection constructor) + `ShadowTlsIngress` (crates/rillane-protocols/src/inbound/shadowtls.rs — handshake relay to the configured handshake site with the v2 challenge-response switch, handing switched streams to the configured inner data server). No UDP face anywhere: ShadowTLS has no UDP carriage (mihomo models it as an SS plugin on the TCP face only), so an SS node carried over shadow-tls takes no UDP connector.
- **Bypass**: the carrier owns its TCP connection (plain dial) — no bottom-socket bypass. The carrier has no addressing face at all; target addressing belongs to the inner protocol — that is the combination boundary (Shadowsocks rides inside with its routing/fake-ip semantics unchanged).
- **Cancel**: open-phase checks (dial + TLS handshake deadline); after the switch the relay is two bidirectional copy halves — dropping either end tears down the connection (peer-observable release)
- **Stats**: relayed-byte counters via the unified EgressConnector face (FlowReport); switch outcomes are named (switched / innocent relay / malformed record) — the protocol has no per-packet observation points
- **Reuse**: one carrier connection per inner SS stream (official v2 has no multiplexing); no prewarm composition
- **Delivery boundary (wire-faithful v2, named refusals)**: challenge = HMAC-SHA1 keyed with the password over every byte the handshake site sent clientward, truncated to 8 bytes, prefixed inside the first fake application-data record (0x17, version bytes 0x03 0x03) after the handshake completes; the server keeps a last-10 hash window (in-flight race tolerance) and falls back to permanent innocent relay after 3 mismatched app-data records or any malformed record shape (first record must be 0x16, record major 0x03, minor ∈ {0x01, 0x03}); post-switch data is fake-record framed both ways with records sized on the official 4096-byte copy buffer (content ≤4091 bytes; the first client record carries the 8-byte challenge ahead of inner data). Wildcard SNI / multi-SNI splitting not delivered (single configured handshake site); v3 strict mode not delivered; innocent visitors must reach the real handshake site (that is the active-probe defense — verified in acceptance).

## vless

- **Conclusion**: the VLESS protocol face is self-written; the REALITY transport face selects the cfal/rustls fork of `rustls` — upstream 049d39b9 (0.23.46) plus 5 REALITY commits (client hooks / target-shaped server hello / isolation hardening / rebase validation), swapped workspace-wide via a `[patch.crates-io]` pin at rev `d17d0fc304c03fe6e2c96ade6cd39c33b951c3af`. The fork's REALITY face deliberately does not authenticate peers (authentication and certificate policy are the caller's job) — authentication (x25519 + HKDF + AES-GCM session-id seal/open, format per the xray REALITY spec) and certificate binding are assembled in rillane-protocols (RIL-107). Alternatives on record: xray-rs (abc15018045126) 1.0.3 is 279 lines of crypto primitives only (derive_auth_key/seal_session_id), no TLS transport or ClientHello crafting — unusable as a transport backend (its MIT auth format serves as reference); shoes (cfal) 0.3.x has a complete REALITY (2940 lines) but keeps `mod reality` private, no library face — unusable; xray-rust (aimalygin) 0.10.0 has a client face with rigorous Go-oracle vectors, but MPL-2.0, not on crates.io, no server face, heavy deps (quinn/h3/ml-dsa) — recorded as a fallback, not taken; reality-rs (YC-Lammy) is a dead placeholder.
- **Version**: requires `rustls = "0.23"` + a `[patch.crates-io]` git pin at `d17d0fc3` (version stays 0.23.46 inside the fork); lock resolves rustls 0.23.46 (fork source), aws-lc-rs 1.18.1
- **License**: Apache-2.0 OR ISC OR MIT (same as upstream rustls; the fork does not change it)
- **Platforms**: all platforms; REALITY record padding depends on the aws-lc-rs backend (see the provider constraint below), which needs a C toolchain — build and tests verified on this machine and CI
- **Public API**: VLESS face `VlessConnector` (crates/rillane-protocols/src/outbound/vless.rs); REALITY face in the fork: `ClientHooks` (start_key_exchange/session_id/server_hello) + `ClientConnection::new_reality` (rejects TLS1.2 configs), `PreparedServerHello::new` (validates a target-shaped ServerHello — TLS1.3 only, 32-byte session_id echo equality, no HRR/PSK/early-data/unknown extensions, a three-suite whitelist, only the target key-share bytes are replaced) + `ServerConnection::new_reality` (rejects non-empty ALPN, client auth, early data, fragment settings)
- **Bypass**: none — the fork owns byte-level ClientHello crafting and record padding (the essence of REALITY); dialing and target connections remain composed by rillane (same shape as the existing TLS face)
- **Cancel**: the fork's connection face is plain tokio AsyncRead/AsyncWrite — open-phase cancellation lives at the task-drop layer (same as the existing TLS face, stated as-is)
- **Stats**: VLESS face as before; REALITY handshake failures surface as named rustls `Error`s (e.g. `PeerIncompatible::RealityUnsupported` — session-id echo mismatch / short-id mismatch takes this shape), never silent degradation
- **Reuse**: no prewarm composition; resumption, early data and compression are disabled on REALITY connections (explicit in the fork — one full handshake per connection), stated as-is; the UDP face (network=tcp only) reuses the node config
- **Provider constraint**: the REALITY flight shaping on both faces (finish_reality → send_reality_record → encrypt_with_padding) pads records to the target's real record lengths; the `encrypt_with_padding` default implementation rejects nonzero padding and only the aws_lc_rs backend implements it — REALITY connections pass the aws_lc_rs provider explicitly, coexisting with the global ring default (explicit per-config, no impact on the existing TLS faces)
- **Fingerprint honesty**: the fork shapes the ClientHello with rustls' own encoder — a rustls-shaped fingerprint, not a uTLS browser clone; anti-probing strength is weaker than the uTLS face; subscription client-fingerprint stays out of the IR (named in the conversion report)
- **Role boundary**: outbound client only (`Vless { reality }` wiring); the fork's server face (PreparedServerHello/ServerConnection::new_reality) serves as the test real-peer; rillane ingress does not catalog a REALITY listener. Legal combinations: reality requires public_key, short_id is optional; flow accepts exactly `xtls-rprx-vision` (delivered in RIL-108 — tcp + TLS/REALITY only, UDP refused; any other flow value is still refused at dial time by name, no silent degradation)
- UDP: network=tcp only (ws/grpc/h2 UDP faces unimplemented, refused by the build-time scan); the UDP face of vless+reality goes through the VLESS UDP face (gate lifted in RIL-107).
- **Server face (RIL-136)**: evaluation sweep (2026-11-16, crates.io API queries `vless`/`xtls` + repo/tarball verification) — no lean VLESS-server library crate exists. xray-rs (abc15018045126) 1.0.3 (published 2026-10-05; MIT) actually ships a full 1:1 Xray-core port — the earlier RIL-107 record ("crypto primitives only") described its REALITY-transport face only — and its `proxy/vless/inbound` Handler does carry a composable-shaped face (`handle_connection(BoxStream, SocketAddr) -> InboundResult{stream, session}`: header decode + UUID validation + response-header write; CMD 0x02 returns the raw stream, the length-prefixed packet relay stays caller-side). ## vless-xtls-vision

- **Conclusion**: self-written framing (RIL-108) — no usable backend exists. Evaluation sweep (2026-11-16, crates.io API queries `xtls`/`vision`/`xray` + GitHub verification): no crates.io crate ships the XTLS Vision (xtls-rprx-vision) framing as a reusable library face; XTLS-Fork/Rust is a dead placeholder (1 commit, 0 stars, README only); xray-wasm (xrayTun) rewrites VLESS+Vision+REALITY in pure Rust but ships as a wasm32-wasip2 component run under wasmtime — not an in-process native library face; xray-rust (aimalygin) implements Vision but is MPL-2.0 and not on crates.io (same blockers as the RIL-107 evaluation — recorded as reference, not taken); xray-rs (abc15018045126) 1.0.3 is crypto primitives only, no framing (on record since RIL-107); jets is a Java implementation. The framing is therefore self-written in rillane-protocols from the Xray-core semantics (shallow-clone read 2026-11-16: `proxy/proxy.go` TrafficState/VisionReader/VisionWriter/XtlsFilterTls/XtlsPadding/XtlsUnpadding, `proxy/vless/encoding/{encoding,addons}.go`, `proxy/vless/outbound/outbound.go`), consistent with the no-backend rule; the cfal/rustls fork is unchanged (Vision lives above TLS and needs no TLS-layer cooperation — the direct-copy switch only requires owning the raw TCP socket below the outer TLS, which rillane already owns).
- **Wire format** (verified from source): request addons carry the flow string as protobuf `Addons{Flow=1}` (`0x0A 0x10 "xtls-rprx-vision"`, OptLen=18; other flows keep OptLen=0). Padding frame: once-per-direction 16-byte user UUID, then `[command(1) contentLen(2 BE) paddingLen(2 BE)] + content + padding`. Commands: Continue=0x00 (next frame follows), End=0x01 (padding ends, traffic stays inside the outer TLS), Direct=0x02 (both sides stop interpreting and switch to the raw TCP socket below the outer TLS). Padding budget (testseed default `[900, 500, 900, 256]`): content < 900 with long padding → `rand(0..500) + 900 - content`, else `rand(0..256)`; capped at `2048 - 21 - content`.
- **State machine**: uplink writer pads while filtering (8 packets) the app traffic for inner TLS records; a ServerHello with the TLS1.3 supported_versions extension arms EnableXtls; the first complete inner ApplicationData record (`17 03 03`, coherent length) then emits Direct and switches to raw writes below the outer TLS. Non-TLS or TLS1.2 inner traffic ends padding with End after the filter window and stays fully inside the outer TLS. Downlink reader mirrors this: UUID-gated frame parse, Continue loops, End returns to plain TLS reads, Direct switches to raw reads.
- **Role boundary**: outbound client only, flow = `xtls-rprx-vision` exactly (other values refused by name as before); requires network=tcp and the TLS/REALITY face (outer TLS must be TLS1.3 — checked post-handshake, as xray does); UDP command refused with vision; not pooled (inline path only — the direct switch is incompatible with pooled borrow semantics).

## xhttp

MASQUE / CONNECT-UDP (RFC 9298 / 9297) — HTTP/3 datagram-capable proxy client face.

- **Conclusion**: **delivered** (RIL-120; self-written client faces on the in-tree HTTP/3 carrier, zero new dependencies; both faces accepted against an in-tree h3 mirror peer and the UDP face additionally against the real `quic-go/masque-go` `cmd/proxy` peer built on this seat). - Spec pinning (RFC 9298 / 9297 section by section; the delivery face implements exactly this):
  - Request (§3.4, identical for HTTP/2 and HTTP/3): HTTP Extended CONNECT — `:method = CONNECT`, `:protocol = connect-udp`, `:authority` = the UDP proxy's authority, `:scheme`/`:path` from the URI Template expansion, plus `capsule-protocol = ?1`. Default URI Template `https://$PROXY_HOST:$PROXY_PORT/.well-known/masque/udp/{target_host}/{target_port}/` (§2; the Well-Known URI is §8.2).
  - Target address forms (§2/§3): `target_host` = DNS name / IPv4 literal / IPv6 literal (**colons MUST be percent-encoded**, e.g. `2001%3Adb8%3A%3A42`); IPv6 scoped zone ids are **not supported**; `target_port` = 1..65535; neither variable may be empty. DNS names are resolved by the **proxy**, and resolution failure MUST be rejected with a 4xx plus `Proxy-Status` (`dns_error`) (§3.1).
  - Response (§3.5): 2xx meeting the Capsule Protocol response requirements is success; **any other response is failure and the client MUST abort the request**.
  - Payload (§5 + RFC 9297 §2.1): over HTTP/3, HTTP Datagrams ride directly in **QUIC DATAGRAM frames** (not capsule-wrapped) — frame body = `Quarter Stream ID` (varint) + `HTTP Datagram Payload`; the MASQUE payload is `Context ID` (varint, **0 reserved for UDP payloads**) + the **unmodified raw UDP octets** (no address headers — the destination address lives in the URI). `Context ID` is a 62-bit variable-length integer; non-zero values are allocated dynamically (even = client, odd = proxy) and MUST NOT be re-allocated within one HTTP namespace; an unknown Context ID is dropped silently or buffered on the order of a round trip.
  - Limits and failures (§5/§3.1/§6.1): a Context ID 0 UDP payload **longer than 65527 bytes MUST abort the stream**; the proxy MUST NOT introduce IP-layer fragmentation (the IPv4 DF bit MUST be set when possible), and oversized datagrams are dropped silently; a proxy MUST NOT queue datagrams to batch them; an inactivity-driven socket close SHOULD NOT use a period below two minutes; the socket's lifetime is bound to the request stream, and an unusable socket MUST close the request stream.
  - HTTP/3 specifics: a datagram is associated with its request by the Quarter Stream ID (request stream ID divided by 4); HTTP/3 Datagrams MUST NOT be sent unless the corresponding stream's send side is open; receiving a datagram associated with a request that has no known datagram semantics aborts the request stream with `H3_DATAGRAM_ERROR (0x33)` (RFC 9297 §2); enabling it requires exchanging `SETTINGS_H3_DATAGRAM` (RFC 9297 §2.1.1).
  - The TCP tunnelling face is outside RFC 9298 (that RFC specifies UDP only) — the CONNECT-IP face is covered by the sibling draft-level specification; that is the CONNECT-UDP/IP split this item records.

## Common transport and reuse matrix (RIL-130)

- **Conclusion**: audit + three actual gaps filled — httpupgrade subscription export face, vless UDP packet encodings (raw/xudp/packetaddr), gRPC gun stream reuse; no new external backend (everything new is self-written against primary sources, verified byte-by-byte). Evaluation sweep (2026-11-16).
- **Current matrix (code face; build-time whitelists + dial-time named refusals in place)**: vless = tcp/ws/grpc/h2/httpupgrade/xhttp (RIL-129); vmess = tcp/ws/grpc/h2/httpupgrade; trojan = tcp/ws/grpc (TLS always); shadowsocks = tcp (SIP003 plugin bridge); anytls/tuic/hysteria2 = native face (TLS/QUIC built in, no network field).
- **UoT (UDP-over-TCP)**: delivered, no gap — anytls outbound UDP face (RIL-106) rides the anytls crate UoT module (uot_sentinel_destination/UotRequest/uot_encode_packet/uot_get_packet_from_stream, pinned in-repo); mihomo outbound schema has no uot transport field for vless/vmess (its SupportUOT() is a UDP-face capability claim, not a config field).
- **XUDP / packetaddr (vless UDP packet encodings)**: no library backend — no standalone xudp/packetaddr crate on crates.io; Xray-core embeds it (not a library); sing-vmess is Go. Self-written against primary sources:
  - Encoding selection = mihomo adapter/outbound/vless.go (source read 2026-11-16): `packet-encoding: packetaddr|packet` → packetaddr, otherwise xudp by default (`packet-addr`/`xudp` legacy booleans). In-repo semantics: default raw (Xray-native UDP face, already accepted), explicit `xudp`/`packetaddr` enable the matching encoding — mihomo's "xudp by default" is not mirrored (documented boundary).
  - xudp frames = sing-vmess v0.2.4 xudp.go line-by-line (mihomo pins v0.2.5, same shape): first datagram `[2B BE metaLen][0x00 0x00][0x01 New][0x01 opt-data][0x02 NetworkUDP][address][8B GlobalID (omitted when zero)][2B BE payloadLen][payload]`; later datagrams `[2B BE metaLen][0x00 0x00][0x02 Keep][0x01][0x02][address][2B][payload]`; downlink same shape (metaLen==4 → session destination; 3=End→EOF, 4=KeepAlive ignored — sing and xray swap 3/4 semantics; the client treats "2=data, 3/4=session close" tolerantly; option bits 0x01 has-payload, 0x02 remote error).
  - Address serializer = sing-vmess protocol.go AddressSerializer (port-first: `[2B BE port][0x01 v4 | 0x02 domain(1B len+str) | 0x03 v6][address]`, same as Xray PortThenAddress).
  - vless carrier header = mihomo transport/vless/conn.go: the Mux branch writes command 0x03 with **no destination address** (version+uuid+addons-len+addons+0x03); the destination appears only in the first New frame.
  - packetaddr frames = sing-vmess packetaddr/conn.go: datagram = `[0x01 v4 | 0x02 v6][address][2B BE port][payload]` (family-first, no domain face — ErrFqdnUnsupported); vless carrier header = command 0x02 + magic address `sp.packet-addr.v2fly.arpa`:443 (packetaddr.SeqPacketMagicAddress); both directions same shape.
  - vmess carrier not self-written: sing-vmess mux/chunk stream (AEAD face) differs from the in-repo vmess UDP face (raw single-target) — non-raw vmess encodings are refused by name at build time.
- **Multiplexing**: mihomo outbound reuse face = gRPC gun stream reuse (grpc-opts `{max-connections, min-streams, max-streams}` — connection cap × per-connection stream bounds); smux/yamux is **not in the mihomo outbound schema** (none of the vless/vmess/trojan Option structs has an smux field; the leftover `smux:` key on wiki sample pages is inert).

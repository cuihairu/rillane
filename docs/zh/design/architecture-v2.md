状态：**设计提案，尚未整体实现**；日期 2026-11-14；当前代码基线 `46c2b12`。本页记录建议决策与迁移门禁，不替代 [当前实现清单](../architecture.md)，也不改变已有稳定发布授权约束。

依据：[竞品研究](../research/proxy-architectures-2026-11-14.md)、[32 个概念及抽象理由](architecture-concepts.md)。本次只产出研究、SVG、概念模型与实施计划；不以文档更新宣称平台代码已交付。

## 1. 需求与明确边界

| ID | 需求 | 验收含义 |
|---|---|---|
| V2-R1 | Linux / OpenWrt / macOS / Windows / Android / iOS | 共用内核与配置语义，各有接管、DNS、退出/恢复和产物验收 |
| V2-R2 | Clash/Mihomo 站点订阅 | 常见完整配置及 provider-only 输入有明确模式，节点/规则/组保真，不等价项明确诊断 |
| V2-R3 | 按进程分别代理 | **仅 Windows、macOS、Linux 本机**；同目标可按本地应用分别选出口 |
| V2-R4 | 网页与游戏同时加速 | 一个数据面实例里并列场景策略，TCP/UDP 都可按证据分类，不能只切换单一 profile |
| V2-R5 | 可解释与可验证 | 能追到来源、规则、配置代际、出口、质量样本与资源影响，不承诺无测量的性能领先 |

OpenWrt 的 LAN 流按设备/IP/端口/域名分流，**不要求识别远端电脑 PID**。Android/iOS 本轮不要求桌面进程归因；移动应用名单可作后续附加能力，不阻断六平台基础代理。iOS 普通 VPN 不承诺任意第三方应用规则；受管 Per-App VPN 另行评估，非普通用户 MVP。

## 2. 总体视图与运行形态

![Rillane 目标架构](/architecture/rillane-target.svg)

桌面/服务器可用一个 rillaned 装配数据面与控制面；路由/驱动等特权操作通过受限 helper 完成。Android 宿主由 VpnService 管理；Apple 宿主由 app + Network Extension 管理。**一个内核不是六平台都必须只有一个 OS 进程**。

关键依赖方向：来源适配 → 规范 IR；IR + 平台能力 → 已验证代际；流上下文 + 代际 → 路由计划；计划 → 会话 → 出口。OS 接管/身份/DNS/旁路通过端口注入。Mesh 和插件均为可选扩展，普通订阅直连标准代理协议。

## 3. 建议决策及为什么采用

以下 A1–A8 是本提案的架构决策建议，不表示代码已经迁移或每个底层 OS API 已选型完成。

| 决策 | 建议 | 原因、收益与代价 | 对应概念 / 需求 |
|---|---|---|---|
| A1 | 单核心，控制面与数据面逻辑分离 | 复用协议与规则；配置刷新不阻塞转发；需要代际发布与取消机制 | C01/C02/C30；R1/R4 |
| A2 | 订阅来源、本地策略、节点目录分离 | provider 刷新不覆盖游戏规则，支持节点删除；需要稳定 ID 与冲突策略 | C09–C14；R2 |
| A3 | 接管、应用归因、路由/DNS变更、socket 旁路拆为平台端口 | Wintun/TUN/packetFlow 并不提供同样身份；复用数据面但平台需分别验收 | C03–C08；R1/R3 |
| A4 | game/web/general 并列，输出 RoutePlan | 同目标按应用选择，场景独立目标；分类和优先级需明确 | C17–C20；R3/R4 |
| A5 | 计划与会话执行分离，旧流绑定代际/出口 | 配置更新与质量变化不逐包重路由；故障旧流可能仍需重建 | C21–C24；R4 |
| A6 | 质量样本带类型/来源/时效，场景有预算与迟滞 | 连接错误不冒充丢包，避免抖动和资源争抢；需要真实测量与调参 | C25–C27；R4/R5 |
| A7 | Mesh/内容检查/WASM 插件可裁剪且不侵入标准代理 | 机场节点不理解自定义 Mesh，OpenWrt/移动需小构建；增加 feature 测试矩阵 | C28/C32；R1/R2 |
| A8 | 桌面 daemon 与移动嵌入共用核心契约，Apple 用公开包接口 | 摆脱 Linux fd 假设与私有 KVC；明确批量、所有权和 IPC，接受复制开销 | C29/C30；R1 |

不采用：六平台强制 PID、把游戏/网页分成两个内核、把所有配置/OS/协议塞入一个 trait、为所有订阅节点强制 Mesh、默认内容 MITM、以 Rust 语言或多跳数量替代性能证据。

## 4. 配置编译与 Clash 兼容

### 4.1 四层配置所有权

1. **SourceSnapshot**：每个订阅的内容及节点/规则版本，原子替换本来源；provider 的刷新参数、凭证引用和失败状态独立。
2. **EndpointCatalog / RuleSet**：来源隔离的稳定对象目录，内置 DIRECT/REJECT 与普通节点区分；显示名可重复，引用不能含糊。
3. **LocalPolicy**：设备入口、DNS、游戏/网页规则、用户选组与限制由用户管理；默认节点导入模式不采纳订阅的入口/系统设置。
4. **RuntimeGeneration**：编译出一致的引用图，检测循环、缺失目标、能力不支持、协议参数错误；只有完整候选成功才发布。

提供 `nodes-only` 与 `full-policy` 两个明确导入模式。前者只吸收节点；后者在来源命名空间内导入组/规则，由本地配置明确引用和设置优先级。不自动允许订阅接管本地监听口、系统路由、插件、文件路径或管理凭证。

### 4.2 兼容分级

| 级别 | 交付范围 | 必须保持的语义 |
|---|---|---|
| L1 节点 | 内联 proxies、provider-only payload、proxy-providers/use | 名称/ID、更新/删除、协议/传输/UDP 能力、凭证引用 |
| L2 策略 | select、url-test、fallback、load-balance，嵌套引用 | 顺序、选择、探测单位、健康/回退与用户偏好；不支持的 chain/relay 变体明确拒绝 |
| L3 规则 | domain/IP/port/process、rule-providers/RULE-SET、支持的逻辑表达式 | 顺序、源/目标端口区别、匹配模式；三桌面进程字段适配；其他平台不静默丢弃关键规则 |
| L4 其他配置 | 按支持表处理 DNS、sniff 等 | 明确启用与覆盖边界；不宣称完整 Clash GUI/API/所有扩展字段兼容 |

正式报告须列输入对象、来源位置、支持等级、输出对象和有损项；严格 full-policy 模式下关键规则/组无法保真即拒绝该候选，保留上一个成功版本。宽松 nodes-only 模式也必须报告丢弃的策略，不把它描述成完整配置转换成功。

动态 provider 使用有界下载、超时、重试、缓存和失效策略；订阅凭证/URL 查询参数不进入日志。周期更新以来源版本替换，不能继续依赖“按名字只追加、规则 extend”。

## 5. 数据面、进程与并行场景

### 5.1 每条流的路径

```text
CapturePort
  → FlowContext（地址/协议/入口/域名证据）
  → 按需 OwnerResolver（三桌面本机）+ DNS/sniff（都有截止时间）
  → 本地优先规则与引用的订阅规则
  → RoutePlan（逻辑组、场景、能力、队列、失败策略、原因）
  → SessionExecutor（固定代际与出口）
  → DIRECT / 标准代理 / 可选受管 Mesh
```

三桌面身份用 PID + 启动身份/连接键 + 可执行路径/用户等组合验证，不能只缓存 PID。名称、完整路径、大小写/匹配模式按各输入格式准确映射；Linux comm 截断不能冒充完整可执行名。首包查询走预算与缓存，权限不足/超时返回 Unknown；平台根本无能力返回 Unsupported。依赖进程身份的配置必须声明 unknown 的拒绝/默认路由策略，不能无提示落直连。

同目标的游戏与浏览器用可信进程规则区分；多个游戏可引用不同组。无身份平台按域名/IP/端口/设备规则分类；不能承诺两个应用同 IP/同端口且没有额外证据时仍可识别。QUIC 网页流是 UDP，游戏也可用 TCP，因此协议类型只是一项约束。

### 5.2 场景策略

| 策略 | 主要目标 | 可用机制 | 明确不保证 |
|---|---|---|---|
| game | 小包尾延迟、会话稳定、可用 UDP | 稳定出口、迟滞选路、队列预算、真实质量源 | 换 IP 后游戏透明不断线、所有线路都更快 |
| web | DNS/代理建连/TTFB 与吞吐 | 合法的连接预热/TLS恢复、域名分流、并发预算 | 自动缓存/解密网站内容、无限提升下载速率 |
| general | 可预测代理与直连 | 显式规则、组选择、能力校验 | 自动知道应用类别 |

旧 `profile: proxy|game|web` 保留为兼容的配置生成预设，展开到新模型；新模型能够同时定义 game/web 两个策略，不新增互斥的运行模式。

## 6. 平台计划与发布要求

![六平台能力矩阵](/architecture/platform-boundaries.svg)

| 平台 | 当前复用面 | 新交付重点 | 本机进程要求 / 验收 |
|---|---|---|---|
| Linux | 已有 TUN TCP/UDP、路由与 /proc 归因 | 接口化、完整名称/权限、DNS/UDP防环与崩溃恢复 | **必须**；同目标不同本地进程，IPv4/IPv6与端口复用 |
| Windows | 交叉构建与安装脚本 | Wintun + 路由/DNS + SCM/权限；独立连接归属实现 | **必须**；WFP/ALE或公开归属查询先实证选型，不能只验驱动 |
| macOS | 打包脚本与平台模型 | 公开接管/应用身份实现、签名/授权、网络恢复 | **必须**；宿主本机应用，helper/extension边界在技术探针后冻结 |
| OpenWrt | Linux核心、musl/procd打包 | fw4/nftables共存、低内存构建、网关DNS与双栈 | **不要求** LAN 客户端进程；按设备/IP/域名/端口验收 |
| Android | VpnService/JNI/测试网段ICMP demo | 复用完整TCP/UDP数据面，protect、前台服务、撤销与切网 | **不要求**桌面进程；应用名单/UID若做为可选能力单独标注 |
| iOS | Swift provider与构建脚手架 | 公开 packetFlow 批次桥接、App/Extension IPC、密钥共享、内存/后台恢复 | **不要求**第三方进程；域名/IP/端口分流，签名设备运行验证 |

双栈、DNS旁路、UDP/QUIC、MTU与切网应分别报告；暂不支持的组合在启动前拒绝或按显式配置降级。Apple 的 packet/app-flow 具体 API、Windows 驱动/归因方案、最低 OS/SDK 版本属于实施前技术探针，不在缺实机数据时伪造定案。

## 7. 质量闭环、资源预算与会话稳定

QualitySample 至少带 `metric_kind / value / source / target / sample_count / observed_at / validity`。区分代理握手、合成 RTT、应用响应、连接失败率、真正包丢失率；用远端回显/序号统计测包丢失时必须有对应对端能力。未知/过期样本不是 0；数据不足不得声称满足 SLO。

游戏和网页各有会话数、拨号、发送队列和内存预算；共享运行时中使用有界队列、公平调度与必要优先级，保证网页也不饥饿。浏览器造成拥塞时验证本地可控瓶颈，不能保证消除 ISP 或第三方出口的排队。下载侧远端瓶颈要靠 OS/受管对端能力或明确无法保证。

健康变化优先影响新流；会话保留出口、代际、源映射和协议状态。安全撤销可强制终止；普通更新可排空旧流。TCP 断开或 UDP 源地址变化可能需要应用重连，不能把“自动回退”写成“无损迁移”。

## 8. 配置切换与安全边界

顺序：下载并形成候选 → 纯验证与引用图检查 → 准备资源 → 计划系统变更 → 应用可回滚变更 → 发布代际 → 旧流排空 → 回收旧资源。错误时保留旧代际并撤回已应用的本实例副作用。系统路由与内存指针不能靠一次赋值获得跨 OS 原子性；须用事务日志、补偿、退出恢复和失败注入证明一致行为。

DNS/fake-IP 映射、已有会话与规则代际关联，不提前复用仍被旧流引用的地址。平台权限变化触发能力重验。控制面、订阅更新与日志脱敏默认有界，秘密按引用保管，不能把 URL token、节点密码或完整应用历史作为高基数指标标签。

Mesh 只对受管且确认能力的节点启用。普通订阅节点仍使用标准协议；UDP Mesh 未有完整安全承载时保持拒绝，不以开发明文旁路作为发布方案。MITM/脚本/插件是显式可选能力，不默认进入游戏热路径。

## 9. 模块落点与替代方案

| 现有模块 | 保留/调整后的职责 |
|---|---|
| rillane-core | Flow、Stream/Datagram、RoutePlan与端口契约；不绑定 OS/订阅格式 |
| rillane-config | 规范 IR、引用/能力验证、兼容旧 profile；不直接改系统路由 |
| rillane-subscription | provider拉取、格式适配、来源版本与诊断；不覆盖本地策略 |
| rillane-platform | 六平台端口实现、能力查询、路由事务、旁路、网络事件与桌面归因 |
| rillane-routing | 条件/动作、组语义、场景目标与可解释评分 |
| rillane-protocols | 标准协议、拨号/传输、连接资源与能力声明 |
| rillane-runtime | 代际编排、会话、预算、各端口装配；逐步拆小现有 runtime_builder |
| rillane-mesh / plugins | 可选受管节点网与插件；不成为最小产物的强制依赖 |
| rillane-ffi / apps / platforms | 移动批次与生命周期API、桌面CLI/daemon、OS宿主与IPC |

先调整接口与模块，只有依赖图、构建裁剪或独立复用确有需要才拆新 crate。替代路线为“直接采用现成内核并开发客户端”：可快速获得平台/订阅能力，但核心行为与升级节奏依赖上游；继续自建则能控制接口与调度，却承担协议兼容、平台维护和测量成本。研究只吸收概念，不复制上游代码；如后续引入代码依赖，须核对所选版本许可证与再分发要求。
